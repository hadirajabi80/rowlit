<a id="advanced-mode"></a>
### Advanced mode (query builder) — حالت Advanced سازنده‌ی پرس‌وجو
حالت SQL سازنده‌ی پرس‌وجو که در آن SQL کامپایل‌شده دستی ویرایش می‌شود. «Back to builder» آن را با `BuilderParser` تجزیه می‌کند؛ SQL بیرون از زیرمجموعه‌ی سازنده (CTE، زیرپرس‌وجو، پنجره…) زبانه را با ذکر دلیل در حالت SQL نگه می‌دارد. *مالک: II-16.*

<a id="appender"></a>
### appender — افزاینده‌ی انبوه سطر
نویسنده‌ای انبوه که بدون INSERTهای SQL به یک جدول موتور سطر اضافه می‌کند (API ‏Appender در DuckDB). ‏`IFederationAppender` در Rowlit مقدارهای درایور را بر اساس kind ستون تبدیل می‌کند و مقداری را که نتواند تبدیل کند NULL ذخیره می‌کند و برای هشدار `conversion` می‌شمارد. *مالک: II-16.*

<a id="ast"></a>
### AST (abstract syntax tree) — درخت نحوی انتزاعی
درختی که تجزیه‌گر از متن SQL می‌سازد: دستورها، بندها، عبارت‌ها و ارجاع‌های جدول به شکل گره‌های تودرتو. تحلیل‌گر پیوند AST ساخته‌ی DuckDB را به شکل JSON از `json_serialize_sql` می‌خواند، پس دستور را دقیقاً همان‌طور می‌فهمد که موتور اجرایش خواهد کرد. *مالک: II-16.* ببینید: تجزیه‌گر (I-08).

<a id="backward-inference"></a>
### backward inference — استنتاج معکوس
حدس زدن جدول از روی ستون‌هایی که پیش‌تر تایپ شده‌اند: در `SELECT name, price FROM |` جدول‌هایی که همه‌ی این ستون‌ها را دارند بالاتر می‌آیند. تکمیل‌کننده آن‌ها را در نمایه‌ای از نام ستون‌های کاتالوگ پیدا می‌کند و ۲۵ امتیاز ارتباط اضافه می‌دهد. *مالک: II-11.*

<a id="binary-safe-text"></a>
### binary-safe text — متن امن برای باینری
نمایش بایت‌هایی که UTF-8 معتبر نیستند به‌صورت متن با escapeهای `\xHH`، در حالی که بایت‌های واقعی حفظ می‌شوند. بسته‌ی Redis در Rowlit متن نمایشی را با یک نگاشت جانبی از آن متن به بایت‌های base64 می‌فرستد تا ویرایش دقیقاً همان بایت‌های اصلی را برگرداند (`BinaryText`). *مالک: II-17.*

<a id="binder"></a>
### binder — پیونددهنده‌ی نام‌ها
بخشی از پردازشگر زبان که نام‌های یک دستورِ تجزیه‌شده را به اشیایی که منظورشان است نگاشت می‌کند. در IntelliSense ‏Rowlit، کلاس `Binder` منبع‌های جدول، نام‌های مستعار، CTEها، جدول‌های موقت و قیدکننده‌ها را به‌صورت تنبل و بدون شکست روی نمایه‌ی کاتالوگ حل می‌کند؛ binder یک DBMS در فصل I-08 همین کار را سخت‌گیرانه انجام می‌دهد. *مالک: II-11.*

<a id="bulk-api"></a>
### bulk API — API انبوه (`_bulk`)
نقطه‌ی پایانی Elasticsearch که در یک درخواست سندهای زیادی را درج، به‌روزرسانی یا حذف می‌کند و بدنه‌اش خط‌های NDJSON از «عمل» و «سند» است. کار import در Rowlit دسته‌های `_bulk` با حداکثر `batchSize` سند و ۵ مگابایت می‌فرستد، در طول بارگذاری `refresh=false` می‌گذارد و در پایان یک بار refresh می‌کند. *مالک: II-18.*

<a id="canonical-sql"></a>
### canonical SQL (builder) — SQL متعارف سازنده
چیدمان متنی ثابت و یگانه‌ای که مدل سازنده‌ی پرس‌وجو به آن کامپایل می‌شود: هر بند در یک خط، کلیدواژه‌ها با حروف بزرگ، شناسه‌ها فقط در صورت نیاز نقل‌قول‌شده، مقدارهای فیلتر به شکل پارامترهای `$fp1…`. دو کامپایلر (TypeScript و C#) باید آن را بایت‌به‌بایت یکسان بسازند. *مالک: II-16.*

<a id="catalog-index"></a>
### catalog index — نمایه‌ی کاتالوگ
ساختار جست‌وجوی درون حافظه که IntelliSense از نمای لحظه‌ای کاتالوگ می‌سازد (`CatalogIndex`). نگاشت نام‌ها برای هر اسکیما با کلیدهای مطابق تبدیل حروف گویش، گراف کلیدهای خارجی در هر دو جهت، اسکیماهای سیستمی داخلی، مترادف‌های PUBLIC در Oracle و کاتالوگ پایگاه‌های داده‌ی دیگر سرور را نگه می‌دارد و اسکیماهایی را که هنوز ندارد از میزبان می‌خواهد. *مالک: II-11.*

<a id="clause-marker"></a>
### clause marker — نشانه‌ی بند
یادداشتی که پارسر جزئی در یک حوزه می‌گذارد: «از این offset به بعد مکان‌نما در بند X است» (`select`، `from`، `join`، `on`، `where`، `set`، `ddl`...). زمینه‌ی مکان‌نما آخرین نشانه‌ی پیش از مکان‌نما را برمی‌دارد تا بداند چه پیشنهاد دهد؛ داده‌ی نشانه جزئیاتی مثل جدولِ مربوط به یک `ON` را حمل می‌کند. *مالک: II-11.*

<a id="codec"></a>
### codec — کدک
قاعده‌ای که بایت‌های یک پیام را به متن خوانا تبدیل می‌کند و برعکس (رشته، JSON، hex، عدد صحیح، Avro، Protobuf، JSON Schema). `MessageCodec` در Rowlit کلید، مقدار و سرآیندهای پیام Kafka را برای مرورگر رمزگشایی و برای ارسال رمزگذاری می‌کند؛ اگر رمزگشایی شکست بخورد به‌جای خطا، hex را با یک متن هشدار نشان می‌دهد. *مالک: II-18.*

<a id="completer"></a>
### completer — تکمیل‌کننده
تابعی که فهرست پیشنهاد را برای یک موقعیت مکان‌نما می‌سازد (`complete` در `intel/complete/completer.ts`). منبع آیتم‌ها را بر اساس بند و قیدکننده انتخاب می‌کند، سپس منبع‌های گویش، پکیج‌ها و ویرایشگر (snippetها، قالب‌های postfix) را اضافه می‌کند و بر اساس امتیاز مرتب می‌کند. *مالک: II-11.*

<a id="completion-item"></a>
### completion item — آیتم تکمیل
یک ردیف از فهرست پیشنهاد: برچسب، نوع (جدول، ستون، کلیدواژه، snippet...)، متنی که درج می‌شود، کلید مرتب‌سازی و مستندات اختیاری. آیتم‌های Rowlit همچنین کلید استفاده برای رتبه‌بندی، ارجاع شیء برای رفتن به تعریف و پرچم `loading` برای ردیف‌های «Loading <schema>…» دارند. *مالک: II-11.*

<a id="confluent-wire-format"></a>
### Confluent wire format — قالب سیمی Confluent
چیدمان بایتی‌ای که تولیدکننده‌ها وقتی پیام Kafka را با اسکیمای Schema Registry سریال می‌کنند به کار می‌برند: یک بایت جادویی `0`، چهار بایت شناسه‌ی اسکیما به ترتیب big-endian و سپس محتوا (Protobuf اندیس‌های پیام را هم اضافه می‌کند). رمزگشای `auto` در Rowlit این قالب را تشخیص می‌دهد و اسکیما را با شناسه‌اش می‌گیرد. *مالک: II-18.*

<a id="cursor-context"></a>
### cursor context — زمینه‌ی مکان‌نما
توصیف جایی که مکان‌نما در یک دستور نشسته است: بند، زنجیره‌ی قیدکننده، پیشوند تایپ‌شده، فراخوانی تابعِ دربرگیرنده، و اینکه پیش از آن یک منبع جدول یا یک عملوند آمده یا نه. `detectContext` آن را از مدل دستور حساب می‌کند و تکمیل‌کننده، راهنمای امضا و موقعیت‌های نوع داده همه از آن می‌خوانند. *مالک: II-11.*

<a id="cursor-es-sql"></a>
### cursor (ES SQL) — مکان‌نمای SQL در Elasticsearch
نشانه‌ای سمت سرور که SQL در Elasticsearch یا OpenSearch وقتی نتیجه بیش از یک صفحه سطر دارد برمی‌گرداند. فرستادن دوباره‌اش صفحه‌ی بعد را می‌آورد و بستنش (`_sql/close`) زمینه‌ی سرور را زودتر آزاد می‌کند؛ تب SQL در Rowlit هر وقت نتیجه جایگزین یا کامل خوانده شود همین کار را می‌کند. *مالک: II-18.*

<a id="database-link"></a>
### database link (Oracle) — پیوند پایگاه داده‌ی Oracle
شیئی در Oracle (`CREATE DATABASE LINK`) که اجازه می‌دهد SQL روی یک سرور Oracle جدول‌های سرور دیگری را به شکل `table@link` بخواند. Rowlit فقط اسکریپت را می‌نویسد؛ موتور هرگز اجرایش نمی‌کند. *مالک: II-16.*

<a id="dedicated-connection"></a>
### dedicated connection — اتصال اختصاصی (Redis)
اتصال Redis جداگانه‌ای که به‌جای مالتی‌پلکسر مشترک برای یک کار باز می‌شود. `RawRedisConnection` مستقیم RESP2 حرف می‌زند و برای MONITOR، دسته‌های MULTI/EXEC/WATCH و فرمان‌های مسدودکننده به کار می‌رود که در غیر این صورت لوله‌ی مشترک را برای همه نگه می‌داشتند. *مالک: II-17.*

<a id="dev-tools-console"></a>
### Dev Tools console — کنسول Dev Tools
ویرایشگری متنی که در آن درخواست‌های خام REST (مثل `GET /_cat/indices`) را با بدنه‌ی JSON می‌نویسید و روی خوشه اجرا می‌کنید، مثل Kibana. Rowlit مسیر را پاک‌سازی می‌کند، متدها را محدود می‌کند، پاسخ را در ۵ مگابایت می‌بُرد و روی اتصال فقط‌خواندنی فقط GET/HEAD و APIهای POST خواندنی را اجازه می‌دهد. *مالک: II-18.*

<a id="diagnostic"></a>
### diagnostic — تشخیص
مشکلی که در متن منبع پیدا شده، با یک بازه، یک شدت (error، warning، info)، یک کد و یک پیام. ویرایشگر تشخیص‌ها را به شکل نشانگر نشان می‌دهد؛ در Rowlit این‌ها از IntelliSense ‏(soft)، از موتور (سرور) یا از آخرین اجرا می‌آیند. *مالک: II-11.*

<a id="dialect-spec"></a>
### dialect spec — مشخصه‌ی گویش
شیء داده‌ای که یک گویش SQL را به IntelliSense یاد می‌دهد (`DialectSpec`): کلیدواژه‌ها، آغازگرهای دستور، نوع‌های داده، کاتالوگ توابع، نقل‌قول، تبدیل حروف، جداکننده‌ی دسته، فهرست کلیدواژه‌ها برای هر موقعیت و قلاب‌های اختیاری (ویژگی‌های lexer، تفکیک‌کننده، دسته‌بند، منبع تکمیل، قواعد قالب‌بند). lexer، تفکیک‌کننده، پارسر، تکمیل‌کننده و قالب‌بند همه آن را می‌خوانند. *مالک: II-11.*

<a id="dry-run"></a>
### dry run — اجرای آزمایشی
اجرای یک عملیات در حالت پیش‌نمایش: محاسبه و نشان می‌دهد چه چیزی عوض خواهد شد، بی‌آنکه چیزی را عوض کند. بازنشانی آفست Kafka در Rowlit همیشه اجرای آزمایشی را اجازه می‌دهد، حتی روی اتصال فقط‌خواندنی، و پنجره‌اش جدول «از/به» را پیش از اعمال نشان می‌دهد. *مالک: II-18.*

<a id="duckdb"></a>
### DuckDB — DuckDB
پایگاه داده‌ی SQL تحلیلی توکار و درون‌فرایندی با موتور ستونی و برداری (مجوز MIT). Rowlit برای هر نشست کنسول پیوندی یک DuckDB درون‌حافظه‌ای قفل‌شده را به‌عنوان موتور فدراسیون اجرا می‌کند (DuckDB.NET؛ در زمان WP0 نسخه‌ی DuckDB v1.5.6). *مالک: II-16.* ببینید: DuckDB SQL (I-17).

<a id="engine-name"></a>
### engine name (wide member) — نام موتوری
نام جدول یگانه‌ای که یک جدول تودرتوی عضو پهن درون موتور فدراسیون می‌گیرد: بخش‌های زیر نام مستعار با نقطه به هم چسبیده و پیش‌فرض‌ها حذف‌شده (`crm.sales.orders` ← `crm."sales.orders"`). ‏`LinkNames.Rewrite` پیش از تحلیل، SQL کاربر را به نام‌های موتوری تبدیل می‌کند. *مالک: II-16.*

<a id="error-tolerant-parsing"></a>
### error-tolerant parsing — تجزیه‌ی خطاپذیر
تجزیه‌ای که با ورودی نامعتبر ادامه می‌دهد و به‌جای خطا بهترین ساختار ممکن را برمی‌گرداند. ویرایشگر به آن نیاز دارد چون دستور هنگام تایپ همیشه ناقص است؛ پارسر جزئی Rowlit روی هر توکن پیشرفت را تضمین می‌کند و شکست‌های خودش را می‌گیرد. *مالک: II-11.*

<a id="explain-mongo"></a>
### explain (Mongo) — توضیح اجرا در Mongo
شرحی که MongoDB از نحوه‌ی اجرای (یا اجرای انجام‌شده‌ی) یک find یا aggregate می‌دهد: کدام نمایه، چند کلید و سند بررسی شد. Rowlit شکل‌های کلاسیک، SBE و sharded را به همان درخت `PlanNode` طرح‌های رابطه‌ای تبدیل می‌کند و برای پیمایش کامل مجموعه و مرتب‌سازی در حافظه هشدار می‌گذارد. *مالک: II-17.*

<a id="explain-sampling"></a>
### EXPLAIN sampling (links) — نمونه‌برداری EXPLAIN
یک `EXPLAIN` ساده روی پیوند از هر منبع حداکثر ۱٬۰۰۰ سطر می‌خواند، چون طرح به داده نیاز ندارد. پرس‌وجوی درونی همچنان تحلیل می‌شود، پس طرح فروراندن واقعی را نشان می‌دهد؛ ‏`EXPLAIN ANALYZE` به‌طور عادی می‌خواند. *مالک: II-16.*

<a id="fdw"></a>
### FDW (foreign data wrapper) — بسته‌بند داده‌ی خارجی
نوعی افزونه‌ی PostgreSQL (postgres_fdw، mysql_fdw، oracle_fdw، tds_fdw) که جدول‌های سرور دیگری را به شکل جدول‌های خارجی محلی در اختیار می‌گذارد. اسکریپت‌های بومی Rowlit سرور، نگاشت کاربر و `IMPORT FOREIGN SCHEMA` را می‌سازند؛ «کل پایگاه داده» به یک import برای هر اسکیمای راه دور تبدیل می‌شود. *مالک: II-16.*

<a id="federated-engine"></a>
### FEDERATED engine (MySQL / MariaDB) — موتور FEDERATED
موتور ذخیره‌سازی MySQL که جدولش داده‌ای نگه نمی‌دارد و هر خواندن را به جدولی روی سرور MySQL دیگر می‌فرستد (در MariaDB: ‏FEDERATEDX). هر بار یک جدول را نگاشت می‌کند و در MySQL به‌طور پیش‌فرض غیرفعال است. *مالک: II-16.*

<a id="federated-query"></a>
### federated query — پرس‌وجوی فدره
یک پرس‌وجو که جدول‌های چند پایگاه داده‌ی مستقل را می‌خواند. در Rowlit این یک SQL در DuckDB روی جدول‌های سوارشده‌ی یک پیوند است؛ منبع‌ها واکشی می‌شوند و سپس دستور بدون تغییر روی موتور محلی اجرا می‌شود. *مالک: II-16.*

<a id="federated-session"></a>
### federated session — نشست فدره
نشست کنسول یک پایگاه داده‌ی پیوندی (`FederatedSession`). فقط پرس‌وجو می‌پذیرد، تراکنش ندارد و پیش از هر دسته جدول‌های سوارشده‌ای را که دسته می‌خواند در زمینه‌ی فدراسیون خودش واکشی می‌کند. *مالک: II-16.*

<a id="federation"></a>
### federation — فدراسیون
پرس‌وجو گرفتن از چند پایگاه داده‌ی جدا، گویی یکی‌اند، بدون ادغام دائمی‌شان. برخلاف شاردینگ (یک مجموعه‌داده که بر اساس کلید روی چند سرور تقسیم شده)، فدراسیون مجموعه‌داده‌های مختلفی را که به سامانه‌های مختلف تعلق دارند join می‌کند. *مالک: II-16.* ببینید: شاردینگ (I-12).

<a id="federation-context"></a>
### federation context — زمینه‌ی فدراسیون
حالتِ پشت یک نشست کنسول پیوندی یا یک پرس‌وجوی یک‌باره روی پیوند: یک نمونه‌ی موتور، محدودیت‌ها و حافظه نهان جدول‌های منبعِ واکشی‌شده. آماده‌سازی‌ها در هر زمینه پشت سر هم اجرا می‌شوند؛ Refresh sources و مادی‌سازی با شناسه‌ی نشست به آن می‌رسند. *مالک: II-16.*

<a id="federation-engine"></a>
### federation engine — موتور فدراسیون
پایگاه داده‌ی محلی که پرس‌وجوی فدره در نهایت روی آن اجرا می‌شود (`IFederationEngine`): اسکیماهایش نام‌های مستعار عضوها و جدول‌هایش منبع‌های واکشی‌شده‌اند. به‌طور پیش‌فرض DuckDB، و SQLite وقتی DuckDB بار نمی‌شود. *مالک: II-16.*

<a id="fetch-relay"></a>
### fetch relay — رله‌ی واکشی
شیئی در موتور که یک کار مرور Kafka را به جریان `kafka.fetch` آن گره می‌زند: یک نشانه‌ی یک‌بارمصرف، یک sink که کار منتظرش می‌ماند و یک لغو که با بسته شدن جریان فعال می‌شود. به کمک آن پیام‌ها روی جریان و پیشرفت و نتیجه روی کار می‌آیند. *مالک: II-18.*

<a id="fetch-request"></a>
### fetch request — درخواست واکشی
آنچه از یک منبع خواسته می‌شود (`FetchRequest`): جدول، تصویر (هرگز خالی)، گزاره‌های عطفی، یک حد اختیاری، سقف سطر و مهلت. ‏`Accept` واکشنده می‌تواند گزاره‌هایی را که نمی‌تواند بنویسد حذف کند و در آن صورت باید حد را هم حذف کند. *مالک: II-16.*

<a id="fk-join-suggestion"></a>
### FK join suggestion — پیشنهاد join بر پایه‌ی کلید خارجی
پیشنهادی پس از `JOIN` که جدول‌های وصل‌شده با کلید خارجی به جدولی از پرس‌وجو را، همراه با یک snippet آماده مثل `orders o ON o.customer_id = c.id`، عرضه می‌کند. Rowlit آن را از گراف کلیدهای خارجی کاتالوگ می‌سازد، کلیدهای مرکب را با `AND` به هم وصل می‌کند و یک نام مستعار یکتا می‌سازد. *مالک: II-11.*

<a id="gateway-seam"></a>
### gateway seam — درز دروازه
یک واسط در لبه‌ی بسته که همه‌ی فراخوانی‌ها به یک سامانه‌ی بیرونی از آن می‌گذرند تا پشتیبان واقعی و جعلی جابه‌جاشدنی باشند. `IMongoGateway` را `DriverMongoGateway` (روی MongoDB.Driver) و `MongoFake` درون‌حافظه‌ای آزمون‌های واحد پیاده می‌کنند. *مالک: II-17.*

<a id="generic-stand-in"></a>
### generic stand-in — جانشین عمومی
مشخصه‌ی گویش موقتی که تا رسیدن یک گویش تنبل‌بار به کار می‌رود: جدول‌های SQLite زیر شناسه‌ی واقعی گویش. باعث می‌شود همه‌ی مسیرهای کد در مدت بار شدن تکه کار کنند (و همچنان `'mysql'`، `'cql'`... ببینند) و اگر تکه بار نشود هم جایگزین آن است. *مالک: II-11.*

<a id="go-to-definition"></a>
### go to definition — رفتن به تعریف
پریدن از یک نام به جایی که تعریف شده (F12 یا Ctrl+کلیک). نام‌های محلی (نام مستعار، CTE، متغیر، جدول موقت) درون ویرایشگر جابه‌جا می‌شوند؛ اشیای کاتالوگ Data tab یا تعریفشان را باز می‌کنند؛ Alt+F12 همیشه DDL را باز می‌کند. *مالک: II-11.*

<a id="golden-test"></a>
### golden test — آزمون golden
آزمونی که خروجی را با یک فایل مورد انتظار ذخیره‌شده مقایسه می‌کند. goldenهای سازنده (`Goldens/Builder/*.json`: کاتالوگ، مدل، SQL، پارامترها، هشدارها) را هم کامپایلر C# و هم کامپایلر TypeScript اجرا می‌کنند و همین آن‌ها را یکسان نگه می‌دارد. *مالک: II-16.* ببینید: فایل golden (II-23).

<a id="hover"></a>
### hover — کارت hover
کارتی که وقتی ماوس روی یک نام می‌ایستد ظاهر می‌شود. Rowlit نوع شیء، توضیح، ستون‌ها با نشان‌های PK/FK (۲۵ ستون اول)، امضای یک روال یا نوع و کلیدهای یک ستون را به شکل Markdown نامطمئن نشان می‌دهد. *مالک: II-11.*

<a id="idle-reaper"></a>
### idle reaper — پاک‌کننده‌ی بیکار
زمان‌سنجی که منابعی را که مدتی کسی از آن‌ها استفاده نکرده می‌بندد. `SourceClientManager` هر 30 ثانیه بررسی می‌کند و کلاینت‌های منبعی را که بیش از `connections.sourceIdleSeconds` (پیش‌فرض 600) بیکار مانده‌اند، مگر اجاره‌ای داشته باشند، می‌بندد؛ مدیر منابع زیر فشار حافظه این حد را کوتاه می‌کند. *مالک: II-17.*

<a id="incremental-lexing"></a>
### incremental lexing — تحلیل لغوی افزایشی
توکن‌بندی دوباره‌ی فقط بخشی از متن که دور ویرایش است و استفاده‌ی دوباره از بقیه‌ی توکن‌های قدیمی. `relex` در Rowlit از ابتدای خط ویرایش‌شده شروع می‌کند و به محض اینکه توکن تازه‌ای با یک توکن قدیمیِ جابه‌جاشده برابر شود می‌ایستد؛ ویرایشی که رشته‌ای را باز کند ممکن است تا انتها دوباره تحلیل کند. *مالک: II-11.*

<a id="intellisense"></a>
### IntelliSense — IntelliSense
خانواده‌ی کمک‌های ویرایشگر که کد را می‌فهمند: تکمیل خودکار، راهنمای امضا، hover، رفتن به تعریف و تشخیص‌های فوری. نام از Visual Studio آمده؛ در Rowlit کتابخانه‌ی خالص TypeScript ‏`ui/src/intel` است که روی نمای لحظه‌ای نهان‌شده‌ی کاتالوگ کار می‌کند و هنگام تایپ هیچ رفت‌وبرگشتی به پایگاه داده ندارد. *مالک: II-11.*

<a id="interrupt"></a>
### interrupt (engine) — قطع پرس‌وجو
متوقف کردن یک پرس‌وجوی در حال اجرا از نخی دیگر. ‏`IFederationEngine.Interrupt` همه‌ی فرمان‌های DuckDB در حال اجرا را لغو می‌کند؛ لغو نشست پیوندی فرمان‌های درایورِ واکشی‌های در حال اجرا را هم لغو می‌کند (در دور QA حدود ۱۲۰ میلی‌ثانیه). *مالک: II-16.*

<a id="join-inference"></a>
### join inference — استنتاج join
پیشنهادهای join سازنده‌ی پرس‌وجو (`infer.ts`): کلیدهای خارجی هم‌منبع (امتیاز ۱۰۰)، رابطه‌های مجازی پیوند (۹۵)، قراردادهای نام‌گذاری (۸۵ یا ۵۵) و نام‌های ستون مشترک شبیه کلید (۷۰ یا ۴۰). پیشنهادی با امتیاز ۸۰ یا بیشتر جدول تازه را خودکار join می‌کند. *مالک: II-16.*

<a id="key-delimiter"></a>
### key delimiter — جداکننده‌ی کلید (Redis)
نویسه‌ای که نام کلیدهای Redis را به سطح‌ها می‌شکند و طبق قرارداد `:` است (`user:1001:profile`). Rowlit آن را برای هر اتصال به کار می‌برد تا درخت پوشه‌ی مرورگر کلید و فضاهای نام تحلیل حافظه را بسازد. *مالک: II-17.*

<a id="language-service"></a>
### language service — سرویس زبان
مؤلفه‌ای که زبانی را آن‌قدر می‌فهمد که به پرسش‌های ویرایشگر درباره‌ی یک سند پاسخ دهد (اینجا چه می‌تواند بیاید، این نام چیست، کجا تعریف شده، چه چیزی اشتباه است). در Rowlit این مؤلفه شیء `Intel` است، یکی برای هر ویرایشگر، بدون وابستگی به DOM یا Monaco. *مالک: II-11.*

<a id="lazy-dialect"></a>
### lazy dialect — گویش تنبل‌بار
گویشی که مشخصه‌اش تکه‌ی کد جداگانه‌ای است و به‌جای قرار گرفتن در bundle اولیه، در نخستین استفاده بار می‌شود. در Rowlit گویش‌های MySQL، ClickHouse، Snowflake، CQL و DuckDB تنبل‌بارند (`ensureDialect`) تا بودجه‌ی bundle رعایت شود؛ تا بار نشده‌اند جانشین عمومی پاسخ می‌دهد. *مالک: II-11.*

<a id="lease"></a>
### lease — اجاره
ادعای شمارش‌شده‌ی «هنوز از این استفاده می‌کنم» روی یک شیء مشترک. جریان‌ها، کارها و دسته‌های Workbench روی کلاینت منبع یک اتصال اجاره می‌گیرند (`AcquireLease`) و پاک‌کننده‌ی بیکار تا وقتی اجاره‌ای هست کلاینت را نمی‌بندد. *مالک: II-17.*

<a id="lexer"></a>
### lexer / tokenizer — تحلیلگر لغوی
برنامه‌ای که متن منبع را به توکن‌ها می‌بُرد (کلمه، رشته، عدد، عملگر، توضیح). Rowlit یک موتور lexer دارد که با جدول‌های گویش هدایت می‌شود و حالت کل سند، حالت خط‌به‌خط برای رنگ‌آمیزی نحوی و حالت افزایشی برای ویرایش‌ها دارد. *مالک: II-11.*

<a id="lexer-hook"></a>
### lexer hook / lexer traits — قلاب lexer / ویژگی‌های lexer
نقطه‌ی گسترش یک گویش در lexer مشترک. گویش‌های تازه‌تر `LexTraits` را به شکل داده اعلام می‌کنند (شناسه با backtick، توضیح با `#`، escape با بک‌اسلش، پیشوندهای پارامتر...) و `traitLexer` آن‌ها را به قلابی تبدیل می‌کند که lexer پیش از قواعد خودش صدا می‌زند، پس هیچ گویشی `lexer.ts` را ویرایش نمی‌کند. *مالک: II-11.*

<a id="librdkafka"></a>
### librdkafka
کتابخانه‌ی کلاینت Apache Kafka به زبان C که Confluent.Kafka آن را برای .NET بسته‌بندی کرده است. چون کد بومی (native) است، Rowlit باید آن را درون موتور منتشرشده بفرستد (روی ویندوز خوداستخراج، روی macOS یک dylib امضاشده کنار apphost) و در CI بررسی می‌کند که بار شود. *مالک: II-18.*

<a id="link-catalog"></a>
### link catalog — کاتالوگ پیوند
ساختار حل‌شده‌ی یک پیوند: برای هر نام مستعار عضو، جدول‌های سوارشده با ستون‌ها، کلیدها و کلیدهای خارجی هم‌منبع، به‌علاوه‌ی رابطه‌های مجازی. برای هر پیوند ۲ دقیقه با کلید اثر انگشت پیوند نهان می‌شود؛ عضوهای پهن فقط ظرف پیش‌فرضشان را در آن دارند. *مالک: II-16.*

<a id="link-definition"></a>
### link definition — تعریف پیوند
آنچه یک پیوند سوار می‌کند (`LinkDefinition`): عضوها، رابطه‌های مجازی، گزینه‌ها و یک نسخه، که در چهار prop از پروفایل اتصال پیوند ذخیره می‌شوند (`members`، `relations`، `options`، `linkVersion`). *مالک: II-16.*

<a id="link-fingerprint"></a>
### link fingerprint — اثر انگشت پیوند
کلید حافظه نهان کاتالوگ پیوند: props سریال‌شده‌ی پروفایل پیوند. هر ویرایش پیوند آن را تغییر می‌دهد، پس کاتالوگ نهان بلافاصله دور ریخته می‌شود، حتی درون TTL دو دقیقه‌ای‌اش. *مالک: II-16.*

<a id="link-member"></a>
### link member — عضو پیوند
یک منبع از پیوند: یک اتصال ذخیره‌شده (رابطه‌ای، MongoDB، Elasticsearch) یا مجموعه‌ای از فایل‌های محلی که زیر یک نام مستعار و با یک دامنه سوار شده است. اعتبارنامه‌هایش در موتور می‌مانند؛ عضوی که خودش پیوند باشد رد می‌شود. *مالک: II-16.*

<a id="link-scope"></a>
### link scope — دامنه‌ی پیوند
اینکه یک عضو چه مقدار از اتصالش را سوار می‌کند: `tables` (فهرست صریح)، `schema` (همه‌ی جدول‌های یک اسکیما)، `database` (همه‌ی اسکیماها) یا `connection` (همه‌ی پایگاه‌های داده). معنای هر سطح به فراهم‌کننده بستگی دارد (`MemberScopes`). *مالک: II-16.*

<a id="linked-database"></a>
### linked database (link) — پایگاه داده‌ی پیوندی
اتصال ذخیره‌شده‌ای با شناسه‌ی فراهم‌کننده‌ی `linked` که به هیچ سروری اشاره نمی‌کند، بلکه جدول‌های اتصال‌های دیگر را زیر نام‌های مستعار سوار می‌کند تا یک پرس‌وجوی DuckDB بتواند آن‌ها را join کند. همیشه فقط‌خواندنی است. *مالک: II-16.*

<a id="linked-server"></a>
### linked server (SQL Server) — سرور پیوندی SQL Server
شیئی در SQL Server (`sp_addlinkedserver`) که اجازه می‌دهد T-SQL به سرور دیگری به شکل `server.database.schema.table` یا از راه `OPENQUERY` برسد. Rowlit اسکریپت را با گذرواژه به شکل جای‌نگهدار می‌نویسد. *مالک: II-16.*

<a id="linked-view"></a>
### linked view — نمای پیوندی
پرس‌وجویی که روی یک پیوند ذخیره شده است: SQL آن یک پرس‌وجوی ذخیره‌شده‌ی معمولی پیوند زیر اسکیمای `views` است و مدل سازنده (اگر باشد) در `linked-views.json` نگه داشته می‌شود. *مالک: II-16.*

<a id="lockdown"></a>
### lockdown (DuckDB) — قفل‌بندی DuckDB
تنظیم‌هایی که پیش از اجرای SQL کاربر روی هر DuckDB فدراسیون اعمال می‌شوند: بدون نصب یا بارگذاری خودکار افزونه، بدون دسترسی بیرونی (فایل یا شبکه)، و سپس `lock_configuration = true` تا دیگر قابل تغییر نباشند. *مالک: II-16.* ببینید: اعمال فقط‌خواندنی (II-19).

<a id="match-score"></a>
### match score — امتیاز تطبیق
میزان تطبیق یک پیشوند تایپ‌شده با یک برچسب: دقیق ۱۰۰، دقیق بدون توجه به حروف ۹۶، پیشوند ۹۰، آغاز کلمه‌ها ۷۰، زیررشته ۵۰، زیردنباله ۲۰ تا ۳۰، بدون تطبیق −۱. برای مرتب کردن فهرست با وزن گروه آیتم (× ۱٬۰۰۰)، امتیاز استفاده و ارتباط جمع می‌شود. *مالک: II-11.*

<a id="materialize"></a>
### materialize (links) — مادی‌سازی
نوشتن نتیجه‌ی یک پرس‌وجوی پیوند در یک جدول واقعی از یک اتصال قابل نوشتن، به شکل یک کار (job)، در حالت create، ‏replace (جایگزینی پس از بارگذاری کامل) یا append. از نویسنده‌ی مقصد و مسیرهای انبوه درون‌ریزی دوباره استفاده می‌کند. *مالک: II-16.*

<a id="member-alias"></a>
### member alias — نام مستعار عضو
نام کوتاهی که عضو زیر آن سوار می‌شود (`crm`): اسکیمای DuckDB جدول‌هایش در SQL. شناسه‌ای با حروف کوچک و حداکثر ۶۳ نویسه، یکتا در پیوند، نه واژه‌ی رزروشده، و نه `main`، `temp`، `system`، `memory`، `information_schema`، `pg_catalog` یا `views`. *مالک: II-16.*

<a id="memory-analysis"></a>
### memory analysis — تحلیل حافظه (Redis)
کاری که با SCAN و `MEMORY USAGE` از کلیدها نمونه می‌گیرد و گزارش می‌دهد حافظه کجا مصرف می‌شود. Rowlit فضاهای نام را در دو سطح جداکننده، 100 کلید برتر، جمع هر نوع و سطل‌های TTL تجمیع می‌کند؛ این یک نمونه است (پیش‌فرض 100000 کلید)، نه سرشماری دقیق. *مالک: II-17.*

<a id="monitor"></a>
### MONITOR — پایش فرمان‌ها
فرمانی در Redis که هر فرمانی را که سرور پردازش می‌کند جریان می‌دهد. برای سرور پرهزینه است، پس Rowlit آن را فقط به‌صورت جریان روی یک اتصال اختصاصی اجرا می‌کند که به‌طور پیش‌فرض پس از 10 دقیقه (حداکثر 60) خودش متوقف می‌شود. *مالک: II-17.*

<a id="mounted-table"></a>
### mounted table — جدول سوارشده
جدول، نما، مجموعه (collection)، نمایه (index در Elasticsearch) یا فایلی از منبع، همان‌طور که در یک پیوند ظاهر می‌شود و با `alias.table` نشانی‌دهی می‌شود. می‌تواند درون پیوند نام دیگری بگیرد (`As`) و گزینه‌های واکشنده داشته باشد. *مالک: II-16.*

<a id="mru"></a>
### MRU / usage store — MRU / استور استفاده
«اخیراً استفاده‌شده‌ها»: رتبه‌بندی‌ای که آنچه پیش‌تر برگزیده‌اید را جلو می‌اندازد. `UsageStore` در Rowlit برای هر آیتم پذیرفته‌شده وزنی با رشد نمایی اضافه می‌کند (نیمه‌عمر ۱۴ روز)، حداکثر ۱۵ امتیاز می‌دهد، حداکثر ۲٬۰۰۰ کلید نگه می‌دارد و برای هر اتصال در تنظیمات ذخیره می‌شود. *مالک: II-11.*

<a id="multiplexer"></a>
### multiplexer (Redis) — مالتی‌پلکسر
`ConnectionMultiplexer` در StackExchange.Redis: شیئی که فرمان‌های همه‌ی صداکننده‌ها را روی یک سوکت pipelineشده برای هر سرور می‌فرستد و خودش دوباره وصل می‌شود. Rowlit برای هر اتصال Redis دقیقاً یکی، درون `RedisClient`، نگه می‌دارد. *مالک: II-17.*

<a id="native-link-script"></a>
### native link script — اسکریپت پیوند بومی
اسکریپتی که Rowlit تولید می‌کند تا یک سرور مقصد با ابزارهای خودش به سرور یک عضو برسد (linked server، ‏FDW، ‏database link، ‏FEDERATED، موتورهای ClickHouse). رازها جای‌نگهدارند و موتور هرگز آن را اجرا نمی‌کند. *مالک: II-16.*

<a id="offset-reset"></a>
### offset reset — بازنشانی آفست
تغییر آفست‌های commit‌شده‌ی یک گروه مصرف‌کننده‌ی Kafka تا مصرف‌کننده‌هایش از جای دیگری بخوانند (اولین، آخرین، یک آفست، یک زمان یا N تا جابه‌جا). Rowlit هر مقصد را به watermarkهای پارتیشن محدود می‌کند و تا گروه عضو فعال دارد از اعمالش خودداری می‌کند (`409 GROUP_ACTIVE`). *مالک: II-18.*

<a id="opensearch"></a>
### OpenSearch
انشعابی متن‌باز از Elasticsearch 7.10 با همان API هسته‌ای REST و افزونه‌های خودش (مثلاً SQL زیر `_plugins/_sql`). Rowlit هر دو را با یک لایه‌ی انتقال پشتیبانی می‌کند و گونه (flavor) را از `GET /` تشخیص می‌دهد. *مالک: II-18.*

<a id="partial-count"></a>
### partial count — شمارش جزئی
شمارش آن‌چه تا این لحظه دیده شده، نه کل سرور. عدد پوشه‌ها در درخت کلید Redis فقط کلیدهای پیمایش‌شده را می‌شمارد؛ سرآیند تا پایان پیمایش «scanned X of ~Y» را نشان می‌دهد. *مالک: II-17.*

<a id="partial-parser"></a>
### partial parser — پارسر جزئی
پارسری که به‌جای پیاده‌سازی یک گرامر کامل، فقط ساختاری را که ابزار لازم دارد می‌فهمد (حوزه‌ها، منبع‌ها، نام‌های مستعار، موقعیت بندها) و بقیه را رد می‌کند. پارسر بازگشتی-نزولی دست‌نوشته‌ی Rowlit از SQL ناقص در نُه گویش یک مدل دستور می‌سازد. *مالک: II-11.*

<a id="pausable-stream"></a>
### pausable stream — جریان مکث‌پذیر
جریانی در موتور که می‌تواند در خود منبع مکث کند، به‌جای آنکه آیتم‌هایش هنگام مکث دور ریخته شوند (`IPausableEngineStream`). دنبال‌کردن زنده‌ی Kafka از این نوع است: مصرف‌کننده را متوقف می‌کند، بروکر پیام‌ها را نگه می‌دارد و پس از ادامه، پیام‌های عقب‌افتاده می‌رسند. *مالک: II-18.*

<a id="pending-definition"></a>
### pending definition — تعریف در انتظار
پاسخ «هنوز چیزی پیدا نشده، ولی اسکیما یا پایگاه داده‌ای که باید آن را در بر داشته باشد در حال بار شدن است». `Intel.pendingDefinition` تکه‌ی گمشده را از میزبان می‌خواهد؛ ویرایشگر «Loading Sales…» نشان می‌دهد و در هر تغییر کاتالوگ تا ۱۵ ثانیه دوباره امتحان می‌کند. *مالک: II-11.*

<a id="plan-warning"></a>
### plan warning (links) — هشدار طرح
یادداشت کددار در یک طرح فروراندن: `rowCap`، `fallback`، `joinKinds`، `joinCollation`، `limitWithoutOrder`، `cartesian`، `decimalWidened`، `conversion`، `fullScan`، `cached`، `fallbackEngine`. کنسول آن‌ها را به شکل پیام چاپ می‌کند. *مالک: II-16.*

<a id="producer"></a>
### producer — تولیدکننده
برنامه‌ای که پیام در تاپیک‌های Kafka می‌نویسد. نمای Produce در Rowlit نقش یک تولیدکننده را دارد: در هر درخواست تا ۱٬۰۰۰ پیام با `acks=all` می‌فرستد و پارتیشن و آفست هر کدام را، به‌علاوه‌ی فیلدهای Avro که اسکیما ننوشته، گزارش می‌کند. *مالک: II-18.*

<a id="push-down"></a>
### push-down — فروراندن
فرستادن بخشی از پرس‌وجو (ستون‌ها، فیلترها، حدها) به سامانه‌ای که داده را نگه می‌دارد تا داده‌ی کمتری جابه‌جا شود. در فدراسیون Rowlit فقط یک بهینه‌سازی است: واکشی می‌تواند سطرهای بیشتری از نیاز برگرداند، هرگز کمتر، و DuckDB همه‌ی گزاره‌ها را دوباره اعمال می‌کند. *مالک: II-16.* ببینید: فروراندن گزاره (I-08)، تصویر، گزاره.

<a id="push-down-plan"></a>
### push-down plan — طرح فروراندن
آنچه از هر جدول سوارشده‌ی یک پرس‌وجو خواسته می‌شد (`PushdownPlan`): متن پرس‌وجوی منبع، تصویر، گزاره‌ها، حد، سقف سطر، وضعیت حافظه نهان و هشدارها. ‏`POST /links/{cid}/plan` آن را بدون واکشی محاسبه می‌کند. *مالک: II-16.*

<a id="pushdown-predicate"></a>
### pushdown predicate — گزاره‌ی فرورانده
شرطی تک‌جدولی به شکل `column OP literal(s)` که می‌تواند به منبع فرستاده شود: `=`، `<>`، `<`، `>`، `<=`، `>=`، `IN`، `BETWEEN`، `LIKE`، `IS NOT NULL`. هرگز IS NULL، ‏OR، تابع، پارامتر یا ستون در هر دو سمت؛ مقدارهای لفظی نوع‌دارند و برای هر گویش نوشته می‌شوند. *مالک: II-16.*

<a id="query-analyzer"></a>
### query analyzer (links) — تحلیل‌گر پرس‌وجوی پیوند
بخشی که AST ساخته‌ی DuckDB از یک دستور پیوند را می‌خواند و برای هر جدول سوارشده تصمیم می‌گیرد کدام ستون‌ها واکشی شوند، منبع کدام گزاره‌ها را می‌تواند ارزیابی کند و آیا حد فرورانده شود (`QueryAnalyzer`). محافظه‌کار است و در صورت تردید به جدول کامل برمی‌گردد. *مالک: II-16.*

<a id="query-builder"></a>
### query builder (links) — سازنده‌ی پرس‌وجو
ویرایشگر بصری پرس‌وجوهای پیوند: جدول‌ها روی یک بوم، joinهای کشیده‌شده بین ستون‌ها، خروجی، فیلترها، گروه‌بندی، مرتب‌سازی و حد، با SQL کامپایل‌شده در کنارش. حالتش یک `BuilderModel` است. *مالک: II-16.*

<a id="query-dsl"></a>
### query DSL — زبان پرس‌وجوی DSL
زبان JSON‌ی Elasticsearch برای جست‌وجو: بدنه‌ای با کلیدهای `query`، `aggs`، `sort`، `highlight` و مانند آن. Rowlit بدنه‌ی کاربر را عبور می‌دهد، `seq_no_primary_term` و شمارش دقیق را اضافه می‌کند، `size` را محدود می‌کند و تکمیل کلیدها و نام فیلدها را بر اساس جای مکان‌نما پیشنهاد می‌دهد. *مالک: II-18.*

<a id="ranker"></a>
### ranker — رتبه‌بند
امتیازدهی‌ای که آیتم‌های تکمیل را مرتب می‌کند: گروه × ۱٬۰۰۰ + امتیاز تطبیق + امتیاز استفاده + ارتباط، منهای ۲۰ برای توابع منسوخ. امتیازها به‌صورت هفت رقم در `sortText` ‏Monaco نوشته می‌شوند تا Monaco ترتیب را نگه دارد. *مالک: II-11.*

<a id="redis-command-table"></a>
### Redis command table — جدول فرمان‌های Redis
فایل `redis-commands.json` با نحو، پیچیدگی، جای کلیدها و پرچم‌های هر فرمان Redis (`readonly`، `blocking`، `transaction`، `blocked` …). موتور از آن برای اعمال فقط‌خواندنی و مسیریابی اختصاصی و رابط برای تکمیل و hover استفاده می‌کند؛ یک آزمون دو نسخه را یکسان نگه می‌دارد. *مالک: II-17.*

<a id="refresh-sources"></a>
### Refresh sources — تازه‌سازی منبع‌ها
فرمانی که کپی‌های واکشی‌شده‌ی منبع‌های یک پیوند را (در یک نشست یا همه) دور می‌ریزد و کاتالوگ پیوند را فراموش می‌کند تا پرس‌وجوی بعدی داده‌ی تازه بخواند. *مالک: II-16.*

<a id="reindex"></a>
### reindex — بازایندکس
کپی کردن سندها از یک یا چند ایندکس Elasticsearch به ایندکسی دیگر، اختیاراً با فیلتر پرس‌وجو یا تغییر با اسکریپت. Rowlit آن را به‌صورت task سمت سرور آغاز می‌کند (`wait_for_completion=false`)، در یک کار موتور هر ۵۰۰ میلی‌ثانیه پیشرفتش را می‌پرسد و با لغو کار، task سرور را هم لغو می‌کند. *مالک: II-18.*

<a id="rejson"></a>
### ReJSON (RedisJSON) — ماژول JSON در Redis
ماژول Redis که یک نوع مقدار JSON با فرمان‌هایی مثل `JSON.GET` و `JSON.SET` اضافه می‌کند. Rowlit آن را با `MODULE LIST` تشخیص می‌دهد و کلیدهای JSON را با فراخوانی‌های ساده‌ی `Execute` ویرایش می‌کند. *مالک: II-17.*

<a id="row-cap"></a>
### row cap (max rows per source) — سقف سطر
بیشترین تعداد سطری که در هر پرس‌وجو از یک جدول سوارشده خوانده می‌شود، به‌طور پیش‌فرض ۲٬۰۰۰٬۰۰۰ (`links.maxRowsPerSource`). از منبع سقف + ۱ سطر خواسته می‌شود تا بریده شدن تشخیص داده شود و طرح آن را با `rowCap` گزارش کند. *مالک: II-16.*

<a id="scan"></a>
### SCAN — پیمایش با مکان‌نما
فرمانی در Redis که فضای کلید را با یک مکان‌نما پیمایش می‌کند و در هر فراخوانی کار محدودی انجام می‌دهد، به‌جای `KEYS *` که سرور را قفل می‌کند. مرورگر کلید Rowlit علاوه بر این هر درخواست را پس از 400 میلی‌ثانیه یا 64 فراخوانی متوقف می‌کند و دکمه‌ی «Scan more» را به کاربر می‌دهد. *مالک: II-17.*

<a id="schema-analysis"></a>
### schema analysis — تحلیل اسکیما (Mongo)
استنتاج شکل یک مجموعه‌ی بی‌اسکیما از نمونه‌ای از سندهایش: مسیرهای فیلد، توزیع نوع‌ها، احتمال‌ها و آمار min/max/distinct. در Rowlit به‌صورت کاری روی 1000 سند (پیش‌فرض) اجرا می‌شود. *مالک: II-17.*

<a id="scoped-source-fetcher"></a>
### scoped source fetcher — واکشنده‌ی دامنه‌دار
واکشنده‌ای که می‌تواند آنچه یک عضو پهن می‌پوشاند را فهرست کند (`IScopedSourceFetcher`): پایگاه داده و اسکیمای پیش‌فرض اتصال، پایگاه‌های داده‌اش و اسکیماهای یک پایگاه داده، فقط نام‌ها. واکشنده‌های رابطه‌ای و MongoDB آن را پیاده می‌کنند. *مالک: II-16.*

<a id="scroll-es"></a>
### scroll (Elasticsearch) — اسکرول
روشی برای خواندن صفحه‌به‌صفحه‌ی کل مجموعه‌ی نتیجه از طریق زمینه‌ای سمت سرور که برای مدت معینی زنده می‌ماند. کار export در Rowlit هر بار ۱٬۰۰۰ سند با زمان زنده‌ماندن ۲ دقیقه اسکرول می‌کند و در پایان اسکرول را پاک می‌کند. *مالک: II-18.*

<a id="search-after"></a>
### search_after
صفحه‌بندی در Elasticsearch با مقدارهای مرتب‌سازی آخرین نتیجه، به‌جای آفست `from` که مدام بزرگ‌تر می‌شود؛ پس صفحه‌های عمیق هم ارزان می‌مانند (همان ایده‌ی صفحه‌بندی کلیدی). وقتی نوار صفحه‌بندی Rowlit `search_after` می‌فرستد، موتور `from` را از بدنه حذف می‌کند. *مالک: II-18.* همچنین: keyset pagination.

<a id="server-diagnostics"></a>
### server diagnostics — تشخیص‌های سرور
خطاهای نحوی‌ای که پارسرِ خود پایگاه داده از راه موتور پیدا می‌کند (`POST /sql/diagnostics`): ScriptDom برای SQL Server و prepare برای PostgreSQL و SQLite. با ۴۰۰ میلی‌ثانیه debounce می‌شوند، درخواست‌های تازه‌تر جایشان را می‌گیرند و کنار تشخیص‌های soft به شکل نشانگر دیده می‌شوند؛ گویش‌های دیگر `NOT_SUPPORTED` پاسخ می‌دهند. *مالک: II-11.*

<a id="shell-json"></a>
### shell JSON — JSON به سبک shell
JSON آسان‌گیری که در shell مربوط به MongoDB تایپ می‌شود: توضیحات، نقل‌قول تکی، کلیدهای بی‌نقل‌قول، لفظ‌های regex و کمک‌تابع‌هایی مثل `ObjectId("…")` یا `ISODate("…")`. Rowlit آن را با یک تجزیه‌گر دست‌نویس که خطاهایش سطر و ستون دارند مستقیم به BSON تبدیل می‌کند. *مالک: II-17.*

<a id="signature-help"></a>
### signature help — راهنمای امضا
کادری که هنگام تایپ آرگومان‌های یک تابع یا رویه پارامترهایش را نشان می‌دهد و پارامتر جاری را برجسته می‌کند. Rowlit ویرگول‌های عمق صفر را می‌شمارد، آرگومان‌های نام‌دار Oracle ‏(`p => v`) و `EXEC p a, b` در T-SQL را دنبال می‌کند و روال‌های کاربر را بر توابع داخلی ترجیح می‌دهد. *مالک: II-11.*

<a id="slowlog"></a>
### slowlog (Redis) — فهرست فرمان‌های کند
فهرست درون‌حافظه‌ی Redis از فرمان‌هایی که از یک آستانه طولانی‌تر اجرا شده‌اند (`SLOWLOG GET`، `SLOWLOG RESET`). Rowlit آن را در تب Slowlog با درخواست می‌خواند و در نمای Logs هم به‌صورت یک منبع لاگ دارد. *مالک: II-17.*

<a id="soft-diagnostics"></a>
### soft diagnostics — تشخیص‌های soft
هشدارهای فوری‌ای که IntelliSense بدون سرور در رابط کاربری حساب می‌کند: رشته‌های بسته‌نشده، پرانتزهای نامتوازن، جدول یا ستون ناشناخته، نام مستعار تکراری، `DELETE` بدون `WHERE` و موارد دیگر. فقط وقتی اسکیمای مربوط بار شده باشد صادر می‌شوند، پس کاتالوگ تنبل هرگز هشدار کاذب نمی‌سازد. *مالک: II-11.*

<a id="source-cache"></a>
### source cache (links) — حافظه نهان منبع
جدول‌های منبعِ واکشی‌شده که برای دستورهای بعدی در موتور نشست می‌مانند. کپی وقتی دوباره استفاده می‌شود که همه‌ی ستون‌های لازم را داشته باشد و هیچ گزاره‌ای نداشته باشد که درخواست تازه ندارد؛ وگرنه واکشی تازه تا ستون‌های کپی قبلی گسترده می‌شود. به‌طور پیش‌فرض روشن است (`links.cacheSources`). *مالک: II-16.*

<a id="source-client"></a>
### source client — کلاینت منبع
تنها handle بلندعمر درایور که موتور برای یک اتصال غیررابطه‌ای نگه می‌دارد (مالتی‌پلکسر Redis، `MongoClient`، کلاینت مدیریتی Kafka …). واسط `IDataSourceClient` را پیاده می‌کند و میان همه‌ی تب‌های آن اتصال مشترک است. *مالک: II-17.*

<a id="source-client-manager"></a>
### source client manager — مدیر کلاینت منبع
سرویس موتور (`SourceClientManager`) که کلاینت‌های منبع را تنبل و فقط یک بار برای هر اتصال باز می‌کند، شکست‌های باز کردن را به `503 SOURCE_UNAVAILABLE` نگاشت می‌کند، رویدادهای `source.client` را منتشر می‌کند و کلاینت‌های بیکار را، مگر اجاره‌ای داشته باشند، می‌بندد. *مالک: II-17.*

<a id="source-fetcher"></a>
### source fetcher — واکشنده‌ی منبع
بخشی برای هر نوع منبع که کاتالوگ یک عضو را می‌خواند و یک جدول سوارشده را به موتور فدراسیون واکشی می‌کند (`ISourceFetcher`: ‏`LoadCatalogAsync`، `Accept`، `Describe`، `FetchAsync`). با شناسه‌ی فراهم‌کننده یا `files` کلید می‌خورد؛ بی‌حالت و ایمن برای چند نخ است. *مالک: II-16.*

<a id="source-kind"></a>
### source kind — نوع منبع
خانواده‌ای که یک فراهم‌کننده به آن تعلق دارد: `Relational`، `KeyValue`، `Document`، `Stream` یا `Search` (`enum SourceKind`). رابط از آن برای انتخاب فضای کاری و موتور برای رد فراخوانی‌های کلاینت منبع روی اتصال‌های رابطه‌ای استفاده می‌کند. *مالک: II-17.*

<a id="source-registry"></a>
### source registry — رجیستری منبع
فهرست همه‌ی شناسه‌های فراهم‌کننده که موتور می‌شناسد (`SourceRegistry`): فراهم‌کننده‌های رابطه‌ای که به‌عنوان نوع `Relational` پیچیده شده‌اند به‌علاوه‌ی فراهم‌کننده‌های غیررابطه‌ای ثبت‌شده، با ترتیب نمایش ثابت برای `GET /providers`. *مالک: II-17.*

<a id="spill"></a>
### spill — سرریز به دیسک
نوشتن داده‌ی میانی پرس‌وجو روی دیسک وقتی در حد حافظه جا نمی‌شود. DuckDB فدراسیون به `<DataDir>/tmp/links/<sessionId>` سرریز می‌کند که با بسته شدن نشست پاک می‌شود. *مالک: II-16.* ببینید: سرریز (I-08).

<a id="splitter"></a>
### splitter (statement splitter) — تفکیک‌کننده‌ی دستورها
مرحله‌ای که آغاز و پایان دستورها و دسته‌ها را پیدا می‌کند. تفکیک‌کننده‌ی Rowlit ‏`;`، ‏`GO [n]` در T-SQL، ‏`/` و بلوک‌های PL/SQL در Oracle، ‏`DELIMITER` در MySQL، بدنه‌های دلاری و خط‌های خالی را مدیریت می‌کند و Ctrl+Enter، پارسر و «اجرای اسکریپت» را هدایت می‌کند. *مالک: II-11.*

<a id="sqlite-fallback-engine"></a>
### SQLite fallback engine — موتور جایگزین SQLite
موتور فدراسیونی که وقتی libduckdb بار نمی‌شود به کار می‌رود: یک SQLite درون‌حافظه‌ای با یک پایگاه داده‌ی attach‌شده برای هر نام مستعار. فقط زیرمجموعه‌ی SQL سازنده را تضمین می‌کند، تجزیه‌گر ندارد (جدول‌های کامل خوانده می‌شوند) و سرریز نمی‌کند. *مالک: II-16.*

<a id="stage-preview"></a>
### stage preview — پیش‌نمایش مرحله
نتیجه‌ی اجرای یک خط لوله‌ی تجمیع فقط تا یک مرحله، که زیر کارت همان مرحله نشان داده می‌شود. Rowlit ‏10 سند را با debounce ‏500 میلی‌ثانیه پیش‌نمایش می‌دهد و در پیش‌نمایش هرگز `$out` یا `$merge` پایانی را اجرا نمی‌کند. *مالک: II-17.*

<a id="statement-model"></a>
### statement model — مدل دستور
ساختاری که پارسر جزئی برای یک دستور می‌سازد: درختی از حوزه‌ها با منبع‌های جدول، CTEها، projectionها، joinها، نشانه‌های بند، زنجیره‌های شناسه، و جدول‌ها و متغیرهایی که دستور می‌سازد. برای هر دستور زیر offset آغاز و متنش نهان می‌شود. *مالک: II-11.*

<a id="statement-scope"></a>
### scope (statement model) — حوزه (مدل دستور)
یک سطح پرس‌وجو درون یک دستور: SELECT اصلی، یک زیرپرس‌وجو، بدنه‌ی یک CTE، یک EXISTS، یک بلوک PL/SQL. هر حوزه صاحب منبع‌ها و نشانه‌های خودش است؛ پیوند `outer` اجازه می‌دهد زیرپرس‌وجوهای همبسته و LATERAL/APPLY منبع‌های بیرونی را ببینند. *مالک: II-11.*

<a id="suggest-guard"></a>
### suggest guard — محافظ پیشنهاد
وصله‌ی کوچکی روی مدل پیشنهاد Monaco ‏(`suggest-guard.ts`) که یک `TypeError` ناشی از بازورود را در Monaco 0.57، وقتی مدل تکمیل در میانه‌ی فراخوانی ناپدید شود، می‌بلعد. هر خطای دیگری دوباره پرتاب می‌شود. *مالک: II-11.*

<a id="symbol"></a>
### symbol — نماد
آن چیزِ نام‌داری که پس از حل شدن زیر مکان‌نماست: نام مستعار، جدول، ستون، CTE، متغیر، تابع، عضو پکیج، اسکیما، پایگاه داده. `symbolAt` آن را یک بار حساب می‌کند و hover و رفتن به تعریف هر دو از آن استفاده می‌کنند. *مالک: II-11.*

<a id="tail"></a>
### tail (live tail) — دنبال‌کردن زنده
دنبال کردن یک لاگ یا تاپیک و نشان دادن ورودی‌های تازه به محض رسیدن، مثل `tail -f`. در Rowlit دنبال‌کردن Kafka یک جریان `kafka.tail` است که از high watermark (یا آفست‌های داده‌شده) شروع می‌کند و قابل فیلتر، مکث و ادامه است؛ رابط تازه‌ترین ۱۰٬۰۰۰ پیام را نگه می‌دارد. *مالک: II-18.*

<a id="task-es"></a>
### task (Elasticsearch) — task در Elasticsearch
عملیات طولانی‌ای که Elasticsearch روی سرور اجرا و زیر `_tasks` منتشر می‌کند (reindex، update-by-query، delete-by-query و…)، با وضعیت و امکان لغو. Rowlit آن‌ها را از راه جریان `es.tasks` زنده نشان می‌دهد و taskهای لغوپذیر را لغو می‌کند. *مالک: II-18.*

<a id="text-fallback"></a>
### text fallback (analyzer) — بازگشت متنی تحلیل‌گر
کاری که تحلیل‌گر پیوند وقتی DuckDB نمی‌تواند دستوری را سریال کند انجام می‌دهد (PIVOT، DESCRIBE، SHOW…): هر جدولی که در متن به شکل `alias.table` آمده کامل و بدون گزاره، با هشدار `fallback`، واکشی می‌شود. *مالک: II-16.*

<a id="token"></a>
### token — توکن
کوچک‌ترین واحدی که lexer تولید می‌کند: کلمه، رشته، عدد، عملگر، نشانه‌ی نگارشی یا توضیح، همراه با offsetها و شماره‌ی خط. توکن‌های Rowlit همچنین نسخه‌ای با حروف بزرگ برای تطبیق کلیدواژه و پرچم `unterminated` دارند. *مالک: II-11.*

<a id="trigger-character"></a>
### trigger character — نویسه‌ی آغازگر
نویسه‌ای که خودش فهرست تکمیل را باز می‌کند. در Rowlit این نویسه‌ها `. ( , @ : # [ "` و فاصله‌اند؛ فاصله فقط پس از واژه‌هایی مثل `FROM`، `JOIN`، `ON` یا `INTO`. *مالک: II-11.*

<a id="ttl-countdown"></a>
### TTL countdown — شمارش معکوس TTL
عمر باقی‌مانده‌ی یک کلید Redis که رابط از TTL خوانده‌شده هنگام بارگذاری کلید معکوس می‌شمارد تا کاربر بدون پرس‌وجوی دوباره رسیدنش به صفر را ببیند. Rowlit زیر 60 ثانیه آن را برجسته می‌کند. *مالک: II-17.*

<a id="type-map"></a>
### type map (links) — نگاشت نوع
قاعده‌هایی که نوع ستون منبع را به kind ستون و نوع DuckDB تبدیل می‌کنند (`TypeMap`)، مثلاً `decimal(p,s)` ← `DECIMAL(38,s)`، ‏`datetimeoffset` ← `TIMESTAMPTZ` در UTC، اعشاری‌های پهن‌تر از ۳۸ رقم ← `VARCHAR` با هشدار. *مالک: II-16.*

<a id="validation-rule"></a>
### validation rule — قاعده‌ی اعتبارسنجی (Mongo)
‏`validator` یک مجموعه (اغلب یک `$jsonSchema`) همراه با یک سطح (`off`، `strict`، `moderate`) و یک کنش (`error`، `warn`، `errorAndLog`) که MongoDB روی درج‌ها و به‌روزرسانی‌ها اعمال می‌کند. Rowlit آن را از `listCollections` می‌خواند و با `collMod` می‌نویسد. *مالک: II-17.*

<a id="virtual-relation"></a>
### virtual relation — رابطه‌ی مجازی
کلید خارجی‌ای که کاربر بین دو جدول سوارشده تعریف می‌کند (معمولاً از عضوهای مختلف، جایی که کلید خارجی واقعی ممکن نیست). کاتالوگ پیوند آن را به شکل کلید خارجی گزارش می‌کند و سازنده از روی آن join پیشنهاد می‌دهد. *مالک: II-16.*

<a id="watermark"></a>
### watermark (low / high) — واترمارک پایین و بالا
اولین آفستی که هنوز در یک پارتیشن Kafka نگه داشته شده (پایین) و آفستی که پیام بعدی خواهد گرفت (بالا). Rowlit آفست شروع، تخمین تعداد پیام، پایان مرور و عقب‌ماندگی را از این دو حساب می‌کند؛ `high − low` در پارتیشن فشرده‌شده یا پاک‌شده فقط کران بالای تعداد پیام است. *مالک: II-18.*

<a id="wide-member"></a>
### wide member — عضو پهن
عضوی با دامنه‌ی `database` یا `connection` که چند اسکیما یا پایگاه داده را می‌پوشاند. جدول‌های تودرتوی آن با سه یا چهار بخش نام‌گذاری می‌شوند و هر بار که چیزی نامشان را بیاورد، ظرف‌به‌ظرف و تنبل بار می‌شوند. *مالک: II-16.*

<a id="wildcard-index"></a>
### wildcard index — نمایه‌ی wildcard
نمایه‌ای در MongoDB روی `$**` (یا `path.$**`) که همه‌ی فیلدهای زیر یک مسیر را نمایه می‌کند و برای سندهایی با فیلدهای متغیر سودمند است. ‏`wildcardProjection` می‌تواند مسیرهایی را شامل یا مستثنا کند و فقط روی یک کلید `$**` تنها برای کل سند مجاز است. *مالک: II-17.*
